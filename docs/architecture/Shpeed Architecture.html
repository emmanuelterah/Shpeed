Shpeed Architecture

An open-source F1 race simulator that fetches public timing data, fits Bayesian models of pace, tyres, strategy and race events, simulates each race lap by lap thousands of times, and publishes a probability for every driver finishing in every position. This page lays out how the parts fit, where the two hard boundaries sit, and what runs over a race weekend.

Decisions the diagram encodes

D1 · ADR-001

Raw data stays on the machine

Timing data is fetched by code and cached locally. Only derived predictions cross the publish boundary, which handles the licensing risk.

D2

One predict path, two callers

The backtester calls the same pipeline as the live run with a historical cutoff. A leakage test fails on any read past it, so backtest scores describe the live system.

D3

Rules live in config

Compound rules, race distance, sprint format and the overtaking-aid era sit in configs/rules/<season>.yaml. The 2026 reset is a data change, not a code change.

D4

Models hand over draws

The engine samples from posteriors rather than point estimates, so model uncertainty flows straight into the probability matrix.

D5

Fitted state is cached

Weekend updates start from the last posterior, keeping the post-qualifying run inside its time budget. NumPyro or variational inference is the fallback if PyMC is too slow.

D6

Components earn their place

Nothing merges unless it beats Plackett–Luce on ranked probability score, and nothing stays if switching it off improves the backtest.

D7 · ADR-002

Transactional store on DuckLake

Syncs commit atomically and every read names a snapshot, so an interrupted sync can't corrupt data and any forecast can be replayed on exactly the data it used.

D8

Core owns the interfaces

Heavy libraries live in adapters behind small ports. The core is pure Python and fast to test; swapping a library touches one adapter.

SOLID: ports and adapters

The core (domain types, the backtester, the race engine, scoring) owns a few small interfaces and never imports FastF1, DuckDB, PyMC or FastAPI. Everything with a heavy dependency is an adapter that implements one of those interfaces, and the CLI wires them together from settings. That one rule delivers most of SOLID at once.

ACID: where state lives

ACID is a property of stored state, so it applies to the four places Shpeed keeps state, not to the simulation maths (which is pure functions plus a seed). The data lake is the one that matters most: Parquet files on their own are not transactional. Shpeed stores them through DuckLake, DuckDB's lakehouse format, which reached v1.0 in April 2026. It keeps a SQL catalog over Parquet files, so every sync is a transaction and every read can be pinned to a snapshot (ADR-002).

Engineering practices

These are set up in Phase 0 and enforced by CI from then on, so they never become a cleanup project later. Each one is a feature in the roadmap tracker.

Testing

Five layers of tests

Unit tests; property tests with hypothesis (matrix invariants, race-state rules); one contract suite per port; integration tests on recorded fixtures with the network blocked; backtest regression and a performance benchmark for model and engine changes.

CI gates

Nothing merges red

Ruff, strict pyright, import-linter layer contracts, 85% coverage on core packages, pip-audit, and the RPS regression gate on model PRs. All required checks on a protected main.

Workflow

Trunk-based, feature-ID driven

Short branches named like feat/P1-02-fastf1-adapter, Conventional Commit PR titles carrying the feature ID, squash merges, and a PR template that repeats the definition of done.

Decisions

ADRs for anything hard to undo

ADR-001 raw data never committed; ADR-002 DuckLake for the store; ADR-003 inference backend, decided at the end of Phase 3 from timings.

Reproducibility

Every output names its inputs

uv lockfile, seeded RNG, snapshot ID, model version and git commit on every prediction and benchmark. Same inputs give a bit-identical matrix.

Releases

SemVer and a changelog

keep-a-changelog entries per PR; tags build the release, the Docker image and the PyPI package through trusted publishing.

Observability

Logs you can follow

structlog JSON with a run_id on every line, timing per pipeline stage, and an alert when a scheduled race-weekend run fails twice.

Security

Least privilege

No secrets in the repo, scoped workflow tokens, Dependabot and pip-audit, a non-root Docker image, and a read-only public API.

Tracking

One ID, end to end

Every feature in the Shpeed Roadmap tracker has an ID, a "done when" test and dependencies. The ID appears in the branch, PR, commit and changelog, and a feature is marked done only when the definition of done is met.

Open questions

  • Is the FastAPI service needed at launch? The Pages site can serve the committed JSON directly. The API could ship as a Docker image for self-hosters only, with no hosting cost.
  • PyMC or NumPyro. Decide at the end of Phase 3 by timing a full weekend update against the post-qualifying budget.
  • OpenF1 as a second source. Worth adding if FastF1 has an outage near a race weekend; otherwise it waits for the in-race stretch goal.
  • Historical odds. An optional market benchmark in scoring, if a clean source turns up.
